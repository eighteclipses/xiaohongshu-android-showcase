# 仿小红书项目后续优化方案

> 生成日期：2026-09-08
> 基线：Android 端（`app/`）+ Express 后端（`server/`）+ 两个 Web 台（创作者平台 `/`、管理后台 `/admin`）
> 前置结论：构建、安装、运行全链路已验证通过；前两轮已完成详情页相关推荐、搜索用户 Tab、搜索联想词、审核原因闭环、创作者数据栏等 8 项优化。

---

## 一、关键发现：三条"半成品链路"

盘点服务端 52 个 API 与 Android `ApiService` 的 26 个接口后，发现**服务端能力已就绪但客户端未接通**的情况，这是当前投入产出比最高的一类工作。

| 服务端接口 | 服务端 | 管理后台 | Android | 现状 |
|---|---|---|---|---|
| `POST /api/posts/:id/report` | ✅ 完整（含重复举报去重） | ✅ 举报处理页（含处理人/备注/时间） | ❌ 无入口、无网络方法 | **整条链路断在客户端**，管理后台"举报处理"永远为空 |
| `GET /api/users/search` | ✅ | — | ❌ 仅查本地 Room | 搜索用户 Tab 换设备后结果不同 |
| `POST /api/auth/refresh` | ✅ | ✅ Web 已做自动续期 | ❌ | token 过期后 Android 需重新登录 |
| `GET /api/notifications` `/read` | ✅ | — | ❌ 全靠本地 Room 消息表 | 通知不跨设备、重装即丢 |
| `GET /api/creators/me/stats` | ✅ | ✅ Web 数据中心在用 | ❌ | Android 数据中心无服务端口径 |

另有两处影响数据可信度的缺陷：

- **视频页未上报浏览**：`VideoViewModel` 中 `recordView` 调用数为 0，所有视频笔记曝光量恒为 0。
- **浏览上报要求登录**：`GraphicViewModel` 第 132 行要求 `loggedInUser != null && token 非空`，游客浏览不计曝光。真实小红书游客曝光同样计数。

## 二、优化项清单（按优先级）

### P0 · 断链补齐 —— 服务端零改动，只改客户端

**P0-1　笔记举报入口（推荐优先做，收益最大）**
- 问题：管理后台有完整的举报处理页和审计日志，但因客户端无入口，实测 `reports: 0`，功能等于空转。
- 方案：`ApiService` 增加 `POST posts/{id}/report` → `RemoteApiClient.reportPost()` → 详情页分享菜单/长按菜单增加"举报"项 → 弹出原因选择（垃圾广告/不实信息/侵权/其他）+ 备注输入 → 提交后 Toast 提示。
- 工作量：约 1 个文件改网络层 + 详情页加菜单 + 一个 Dialog。
- 收益：接通整条内容治理闭环，管理后台举报处理页首次可被真实数据验证。

**P0-2　搜索用户走服务端**
- 方案：搜索结果用户 Tab 在查本地 Room 之外，并发调用 `GET /api/users/search?keyword=`，按 id 去重合并；断网时静默保留本地结果（与现有笔记搜索的降级策略一致）。
- 收益：用户搜索结果与服务端一致，不再受本地库限制。

**P0-3　token 自动续期**
- 方案：在网络层统一拦截 401，调用 `POST /api/auth/refresh` 续期后重试一次；失败再跳登录。Web 端已有同类实现可参照。
- 收益：避免用户在使用中被踢出登录。

---

### P1 · 数据真实性

**P1-1　视频页补浏览上报**
- 方案：`VideoViewModel.init()` 中复用与图文页一致的 `recordView` 调用。

**P1-2　游客浏览计入曝光**
- 方案：去掉 `GraphicViewModel` 中要求登录的前置判断，未登录时用设备 ANDROID_ID 作为 `visitorKey`（服务端 `optionalAuth` 已支持匿名上报）。
- 注意：需确认是否会影响"作者本人浏览自己笔记"的统计口径，建议服务端侧顺带排除作者自身浏览。

---

### P2 · 真实小红书核心体验缺口

| 项 | 现状 | 方案 | 说明 |
|---|---|---|---|
| 服务端评论树 | 评论回复关系、评论点赞**只存本机 Room** | 服务端 comments 表增加 `parent_id`、`like_count`；客户端改为读写服务端 | 解除"换设备/重装后回复关系丢失"这一已知限制，需数据库迁移 |
| 主页背景图 | 字段与远程读取已备，**无设置入口** | 编辑资料页增加背景图选择 | 成本低 |
| IP 属地 | 写死"福建" | 按用户资料设置字段，或按注册/登录 IP 段解析省份 | 真实 IP 库需外部数据源，建议做成可配置字段 |
| 群聊 | 占位说明页 | 服务端需新建会话模型 | 工作量较大，视优先级 |
| 同城 LBS | 本地公开笔记流 | 接入定位 + 笔记坐标过滤 | 依赖真实地理数据 |

---

### P3 · 工程质量

- **Room 主线程查询治理**：`allowMainThreadQueries()` 仍开启，存量代码大量主线程同步读库。建议按模块分批改 ResultSet 到 Repository 层，配合协程/线程池。属于重构级工作，建议单独立项。
- **自动化测试**：目前只有模拟器 GUI 走查，无自动化测试。建议先补 `server/smoke-test.js` 之外的接口测试，再考虑 Android 端 Espresso 关键路径用例。
- **已知缺陷文件**：项目根目录残留 `hs_err_pid*.log`、`replay_pid*.log`、`ui_dump*.xml`、`xhs_db*.db` 等调试产物（累计约 5MB），建议清理或加入 `.gitignore`。

---

### P4 · Web 两端

**创作者服务平台**
- 单篇笔记数据详情：真实小红书每篇笔记可下钻看曝光/阅读/互动/涨粉，目前只有列表级汇总。
- 数据中心补充粉丝增长趋势（需服务端先记录粉丝变更历史）。

**管理后台**
- 数据概览增加趋势图（近 7/30 天笔记量、用户增长）。
- 笔记审核支持批量通过/驳回（当前逐条操作）。
- 审计日志增加按操作类型筛选。

## 三、建议执行顺序

| 批次 | 内容 | 理由 |
|---|---|---|
| 第 1 批 | P0-1 举报入口、P1-1 视频浏览上报、P1-2 游客曝光 | 改动小、立即见效，且能激活现有空转功能 |
| 第 2 批 | P0-2 用户搜索上服务端、P0-3 token 续期 | 需要改动网络层，风险略高，建议与第 1 批分开验证 |
| 第 3 批 | P2 服务端评论树 | 涉及数据库迁移，需单独备份与回归 |
| 第 4 批 | P4 Web 端增强 | 独立于 Android 端，可并行 |

---

## 四、风险与依赖

1. **评论树改造（P2）需数据库迁移**：当前 Room `version = 9`，服务端为 MySQL + JSON 双模。改动前必须备份 `server/data.json` 与 MySQL 库。
2. **游客曝光放开（P1-2）会改变统计口径**：现有 16 次浏览的基线会快速上升，若用于演示需提前说明。
3. **P0-2 / P0-3 依赖后端在线**：本地无后端时必须有静默降级，不能弹出报错打断用户。
4. **IP 属地、同城 LBS 依赖外部数据源**：若无真实数据源，建议维持"可配置字段 + 默认值"的演示实现，不要硬编码。
